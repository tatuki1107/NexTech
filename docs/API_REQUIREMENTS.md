# 要件定義書とAPIの対応

共有されたNexTech要件定義書の5.2〜5.8をAPIレベルで満たすための実装範囲です。
URLはすべて `/api/v1` 配下です。詳細な入力・出力は
[OpenAPI](../Backend/app/openapi/index.yaml) を正とします。
Frontendのログイン・申込・管理画面との接続は別作業です。

| 要件 | APIの対応 |
| --- | --- |
| 5.2 検索・詳細 | `GET /events`、`GET /events/:eventId`。キーワードはイベント名・概要・主催者名の部分一致。`organizerName` による絞り込み、東京時間の開催日、タグ/カテゴリ・形式・空席条件 |
| 5.3 申込・キャンセル | `POST /events/:eventId/registrations`、`DELETE /events/:eventId/registration`。定員・待機・繰り上げ。`waitlistPosition` は現在の順位で、キャンセル・繰り上げ後の欠番を利用者に見せない |
| 5.4 作成・編集・公開 | `POST /organizers/:organizerId/events`、`PATCH /events/:eventId`、`PATCH /events/:eventId/status`。所属・所有する主催者のイベントを直接公開でき、変更履歴・操作ログを保存 |
| 5.5 募集・参加者・受付 | `GET /events/:eventId/recruitment-summary`、`GET /events/:eventId/registrations`、受付API。氏名・メール・申込番号の部分一致と `registrationId` の完全一致検索 |
| 5.6 マイページ・興味・後継イベント | 既存の `/me/registrations`・フォローAPI、および `GET /me/recommended-events`。終了した参加履歴と共通する主催者/タグから次のイベントを取得 |
| 5.7 運営管理 | `/admin/events`・`/admin/organizers`・`/admin/registrations` の一覧/詳細、主催者状態変更、対象別履歴、`POST /admin/reviews`、`GET /admin/moderation-actions` |
| 5.8 集計 | 月別開催数・参加者推移、人気カテゴリ・主催者、`GET /admin/analytics/breakdown` のカテゴリ/主催者/形式別集計。期間・主催者・カテゴリ・形式で絞り込み |

## 公開と運営権限

- 通常の主催者は自組織のイベントを直接公開できます。管理者による事前承認は不要です。
- 他組織のイベントは操作できません。停止中の主催者は公開・運営操作を行えません。
- 管理者がイベントを `draft` に変更した場合は運営による公開停止とし、主催者による再公開を
  拒否します。主催者は内容を修正できますが、公開再開は管理者の `published` 指定が必要です。
  既に下書きのイベントにも公開停止を設定できます。
- 管理者による公開停止・解除は既存の `moderation_actions` に記録します。
  `metadata.eventVersion` で対応するイベント版を記録し、同時刻の履歴も判別します。
- `cancelled` は中止の終端状態で、下書き経由でも再公開できません。
- 主催者を `inactive/suspended` にすると、公開・新規申込・受付等を止めます。
  `active` への復帰は元のイベント状態に従った再表示となり、個別の運営公開停止は解除しません。
- `/admin/*` は管理者のみ利用できます。公開/停止・状態変更・確認記録・主催者編集の履歴を保存します。

## 待機順位と推薦

- DBの `waitlist_position` は並び順キーとして維持します。APIは現在の待機列を数えた順位を返します。
  待機1番が繰り上がった場合、次の利用者の表示順位は1番です。
- 定員増加時も既存の待機者を先着順で繰り上げます。新規申込・キャンセルと同じイベント行ロック内で
  定員確認・状態履歴・通知を更新し、後からの申込による追い越しを防ぎます。無効・削除済みアカウントは繰り上げません。
- 非公開中の増員は再公開時に繰り上げます。主催者による再公開・管理者による公開停止解除の両方が対象です。
  状態変更と繰り上げ・履歴・通知は同一トランザクションで行い、同じ公開状態への再指定では重複処理しません。
- 推薦元は終了済みイベントの `confirmed/checked_in` 履歴です。
  `pending/waitlisted/cancelled/no_show` は推薦元にしません。
- 推薦先は有効な主催者の公開・開始前・締切前イベントです。同一主催者または共通タグが条件です。
  申込済みイベント、非公開・限定公開イベント、参加URLは返しません。履歴がなければ空配列です。
- このMVPでは機械学習や人気順の推測ではなく、明示的な関連条件と開催日順を使います。

## 集計ルール

- 日付検索・集計は東京時間（`Asia/Tokyo`）の開始日0時以上・終了日の翌日0時未満です。
  DB/OSのタイムゾーンをUTCにしても結果は変わりません。
- 運営参加情報一覧の期間は **申込日**、集計APIの期間は **イベント開催日** に適用します。
- 集計対象は `published/completed` のイベントです。下書き・中止は除外します。
- 集計期間は最大3660日、ランキング・軸別集計は最大100件です。
  月別集計は該当イベントがない月も0件で返します。

| 出力 | 定義 |
| --- | --- |
| `eventCount` | イベント数。申込のJOINで二重計上しない |
| `registrationCount` | キャンセル以外の申込件数。待機を含む |
| `participantCount` | 月内の `confirmed/checked_in` のユニークユーザー数。同じ人の複数参加を重複させない |
| `confirmedCount` | 枠を使用する `pending/confirmed/checked_in/no_show` の件数 |
| `attendedCount` | `checked_in` 件数 |
| `capacity` | イベント定員の合計。申込数に関係なく各イベント1回だけ加算 |
| `applicationRate` | `registrationCount / capacity`。待機を含むため1（100%）を超えることがある |

確認済み記録の `reviewedAt` は最終確認時刻です。その後の編集がないことを保証するフラグではなく、
対象の `updatedAt` と比較して再確認を判断します。
未記録だった過去の主催者編集履歴は復元できません。

## 検証範囲・残作業

- 要件対応は `Backend/app/test/requirements.integration.test.ts`、既存不具合は回帰テストで確認します。
- DB構造・既存マイグレーションは変更しません。既存データを保持します。
- PostgreSQL 16の専用DBで統合テスト、並行申込・同一版への並行編集、既存マイグレーションとデータの保持を確認します。
  本番相当の負荷試験、HTTPS・バックアップ・可用性の運用確認は別途必要です。
- 画面との接続、受付取消の要否、独立した参加条件入力欄など、要件書で詳細が未確定の点は別途整理します。

## 編集・認証の安全性

- `PATCH /events/:eventId` は `expectedVersion` が必須です。取得した `Event.version` を送ります。
  未指定は400、現在の版と異なる場合は409 `VERSION_CONFLICT` です。競合時は再取得して利用者に差分を確認してもらいます。
  例: `{"title":"更新タイトル","expectedVersion":3}`。自動で版番号だけ更新して再送しないでください。
- 論理削除済みユーザーは、ログイン・アクセストークン利用・リフレッシュをすべて拒否します。
- 認証ログとIP制限には実際のソケット接続元を使い、クライアントが送る `X-Forwarded-For` は信用しません。
  ログインにはアカウント別の制限も適用します。プロキシ配下ではIP制限がプロキシ単位になる点に注意してください。
- 回数制限のメモリには件数上限と期限切れ掃除があります。ただしカウンターはプロセスごとで、
  複数インスタンス間の共有や再起動後の継続には外部の共有ストア／入口側のレート制限が必要です。
