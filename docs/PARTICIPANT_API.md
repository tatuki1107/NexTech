# 参加者画面とAPIの接続

## 構成

ブラウザ → Next.js `/api/v1/*` → Backend `/api/v1/*` → PostgreSQLの経路で接続します。
Backendの接続先はNext.jsサーバーの `INTERNAL_API_BASE_URL` で設定します。
既定値は `http://localhost:3001`、Docker Composeでは `http://backend:3001` です。
ブラウザにBackendの内部URLやアクセストークンを渡しません。

| 画面・操作 | 接続API（`/api/v1` 配下） |
| --- | --- |
| 新規登録・ログイン・ログアウト | `POST /auth/signup`, `/auth/login`, `/auth/logout` |
| セッション更新 | `POST /auth/refresh` |
| 検索・イベント詳細 | `GET /events`, `/events/:id` |
| 申込・キャンセル | `POST /events/:id/registrations`, `DELETE /events/:id/registration` |
| マイページ | `GET /me`, `/me/registrations`, `/me/recommended-events` |
| 保存イベント | `GET /me/saved-events`, `PUT/DELETE /me/saved-events/:id` |
| 興味・主催者フォロー | `GET /categories`, `/me/favorite-categories`, `/me/favorite-organizers`, `PUT/DELETE /me/favorite-{categories,organizers}/:id` |
| 通知・既読 | `GET /me/notifications`, `PUT /me/notifications/:id/read`, `/me/notifications/read-all` |
| プロフィール・通知設定 | `PATCH /me`, `GET/PATCH /me/notification-settings` |

## 認証・通信

- Next.jsはログイン・更新レスポンスからアクセストークンを取り出し、HttpOnly / SameSite=Lax Cookieに保存します。JSONからはトークンを除去します。
- BackendのHttpOnlyリフレッシュCookieは `/api/v1/auth` のパスを維持して中継します。個人データのAPIにはリフレッシュCookieや他のCookieを転送しません。
- アクセストークンは900秒で失効します。401を受けたクライアントは更新し、元のリクエストを一度だけ再試行します。
- 同一タブの更新要求はまとめ、Web Locks対応ブラウザではタブ間の更新も直列化します。ロック取得後にCookieの更新済み状態を再確認します。
- BroadcastChannel対応ブラウザでは登録・ログイン・ログアウトを他のタブにも通知し、個人表示を消してから再取得します。遅れて届いた旧セッションの応答は適用しません。
- 更新APIの401は未ログイン扱いとし、接続障害・502は再試行可能なエラーとして扱います。
- HTTPS・本番環境ではアクセストークンCookieにSecureを付けます。本番の利用にはHTTPSが必要です。
- 更新操作にはOriginとアクセス先Hostの一致が必要です。Next.js内部のホスト名との違いを考慮し、転送Hostヘッダーを判定に使いません。リバースプロキシではHostとプロトコルを正しく引き継いでください。
- 中継対象は参加者向け操作のみです。主催者・管理者の更新APIを任意に中継する汎用プロキシにはしていません。
- 個人データと認証レスポンスはキャッシュせず、内部例外・内部URLはエラーに含めません。

## 表示と操作

- 個人ページは未ログイン時にログインへの導線を表示します。ログイン後はアプリ内の元のURLに戻します。
- 読込中・データなし・APIエラーを表示し、保存・申込・設定更新の失敗時に成功扱いにしません。
- イベント検索はv1の全ページを取得して既存の検索UIへ渡します。カテゴリに加えてAPIのタグ名も検索対象です。
- 個人一覧もページングを最後まで取得します。件数が大きくなる場合は、画面側ページング・サーバー検索への移行が必要です。
- 保存はアカウント単位でDBに保持し、従来のブラウザ内ブックマークや固定サンプルは参照しません。旧localStorageの保存内容は自動移行しません。
- 申込は参加確定・キャンセル待ちを区別します。キャンセルは確認操作を挟み、成功後に表示を再取得します。最終的な定員・期間・権限の判定はBackendが行います。
- ログインの復元を待ってイベント詳細を取得し、失効からの復帰時に未ログイン状態の参加情報を表示し続けないようにします。
- 公開終了等で詳細APIが404の場合、本人の `/me/registrations` にある情報だけを履歴として表示します。非公開の説明や参加URLを復元・推測しません。
- 公開停止・非公開でも、開催前の `pending/confirmed/waitlisted` の本人の申込にはキャンセル導線を表示します。非公開イベントへの新規申込・再申込は表示せず、受付済み・欠席・開催後の申込もキャンセル対象にしません。最終判定はBackendが行います。
- 主催者の新規フォロー候補は公開イベントにある主催者と既存フォローから表示します。独立した全主催者ディレクトリではありません。

## 検証

Frontendディレクトリで `bun test`、`bun run lint`、`bunx tsc --noEmit`、`bun run build` を実行します。
`test/api-proxy.test.mjs` は中継の許可範囲・Origin・Cookie・トークン非公開・内部例外の秘匿を、
`test/api-client.test.mjs` は更新の同時実行・更新障害・ログイン失敗・ページングを検証します。
専用のPostgreSQLと実Backendを使うブラウザ検証では、登録→保存→申込→待機→取消・繰り上げ、
プロフィール・通知設定・フォロー・既読のDB保存、セッション更新、アカウント分離を確認します。

この接続は参加者画面が対象です。主催者画面の仮データ接続や管理者画面の新規実装は含みません。
