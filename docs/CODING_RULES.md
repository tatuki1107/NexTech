# NexTech コーディングルール

この文書は、NexTechのFrontendとBackendに共通する実装基準です。

ルールの強さは次の表記で示します。

- **MUST**：必ず守る。例外が必要な場合はレビューで理由を説明する。
- **SHOULD**：原則として守る。合理的な理由があれば例外を認める。
- **MAY**：状況に応じて採用できる推奨事項。

機械的に確認できる事項は、文書だけでなくESLint、TypeScript、Formatter、CIの設定へ
順次移します。ツールの設定とこの文書が矛盾する場合は、チームで意図を確認して
どちらかを更新します。

## 1. 共通原則

- **MUST** TypeScriptの `strict` モードを維持する。
- **MUST** 目的の異なる処理を1つの関数やコンポーネントに詰め込まない。
- **MUST** 秘密情報、認証情報、個人情報をコードやログへ直接記録しない。
- **MUST** 警告、型エラー、Lintエラーを放置したままマージしない。
- **SHOULD** まず読みやすい単純な実装を選び、必要になる前の共通化を避ける。
- **SHOULD** コメントには処理内容の言い換えではなく、判断理由や制約を書く。
- **SHOULD** 変更範囲を小さく保ち、無関係なリファクタリングを混ぜない。

## 2. TypeScript

- **MUST** `any` は原則使用しない。外部入力には `unknown` を使い、検証してから扱う。
- **MUST** 型エラーを `@ts-ignore` で隠さない。やむを得ない場合は理由と解消条件を書く。
- **MUST** APIレスポンス、関数の引数、共有データ構造には明確な型を定義する。
- **SHOULD** 型だけのimportには `import type` を使う。
- **SHOULD** 不変の値には `const` を使い、再代入が必要な場合だけ `let` を使う。
- **SHOULD** 複数の意味を持つboolean引数を避け、オプションオブジェクトや別関数を使う。
- **SHOULD** 強制的な型アサーションより、型ガードやバリデーションを優先する。

```ts
// Avoid
function readMessage(value: any) {
  return value.message;
}

// Prefer
function hasMessage(value: unknown): value is { message: string } {
  return (
    typeof value === "object" &&
    value !== null &&
    "message" in value &&
    typeof value.message === "string"
  );
}
```

## 3. 命名

| 対象 | 形式 | 例 |
| --- | --- | --- |
| 変数・関数 | `camelCase` | `userProfile`, `getUser` |
| Reactコンポーネント・型 | `PascalCase` | `UserProfile`, `ApiError` |
| 固定の定数 | `UPPER_SNAKE_CASE` | `MAX_RETRY_COUNT` |
| boolean | `is`、`has`、`can`、`should` | `isLoading`, `hasPermission` |
| イベントハンドラー | `handle` + 対象 | `handleSubmit` |

- **MUST** 役割が伝わらない1文字名や、意味の曖昧な省略形を避ける。
- **SHOULD** 関数名は `get`、`create`、`update`、`delete`、`validate` などの動詞から始める。
- **SHOULD** 配列やコレクションは複数形にする。
- **SHOULD** ファイル名は、そのファイルの主な責務が分かる名前にする。

## 4. 関数とモジュール

- **MUST** 関数は1つの明確な責務を持つ。
- **MUST** 外部入力は処理の境界で検証する。
- **SHOULD** 副作用のない処理と、通信・ファイル操作などの副作用を分離する。
- **SHOULD** ネストが深くなる場合は、早期returnや関数分割を使う。
- **SHOULD** 例外を握りつぶさない。利用者が適切に処理できる形へ変換する。
- **MAY** 同じ知識が複数箇所で繰り返された時点で共通化する。

## 5. Frontend（Next.js・React）

- **MUST** Server Componentを基本とし、状態、Effect、ブラウザAPIが必要な境界だけ
  `"use client"` を付ける。
- **MUST** 読み込み中、データなし、エラー、成功の各状態を考慮する。
- **MUST** ボタンやフォームには適切なHTML要素を使い、キーボード操作を妨げない。
- **MUST** 画像、入力欄、アイコンのみのボタンには用途が伝わる代替情報を用意する。
- **SHOULD** データ取得や変換処理を表示専用コンポーネントへ散在させない。
- **SHOULD** ページ固有の部品と、複数画面で再利用する部品を区別する。
- **SHOULD** Propsは必要最小限にし、巨大なオブジェクトをそのまま渡さない。
- **SHOULD** `useEffect` は外部システムとの同期に使い、計算可能な値の生成には使わない。
- **SHOULD** Tailwind CSSのクラスが読みづらくなった場合は、部品分割やスタイルの整理を行う。
- **MUST** Next.js固有の実装では、リポジトリに導入されているバージョンの仕様を確認する。

## 6. Backend（Bun・Elysia）

- **MUST** パス、クエリ、ヘッダー、本文などのリクエスト値を検証する。
- **MUST** 成功・失敗に対応した適切なHTTPステータスコードを返す。
- **MUST** 内部スタックトレース、秘密情報、DBの詳細をクライアントへ返さない。
- **MUST** 環境依存値は環境変数から取得し、起動時に必要項目を検証する。
- **SHOULD** ルート定義、入力検証、業務ロジック、データアクセスの責務を分ける。
- **SHOULD** APIのエラーレスポンスを次の形式に統一する。

```json
{
  "error": {
    "code": "USER_NOT_FOUND",
    "message": "ユーザーが見つかりません"
  }
}
```

- **SHOULD** `code` はプログラムで判定できる安定した値にし、`message` は利用者が理解できる
  内容にする。
- **SHOULD** CORSは許可する接続元を環境ごとに明示し、本番環境で無制限に許可しない。

## 7. エラー処理とログ

- **MUST** エラーを無視する空の `catch` を作らない。
- **MUST** ユーザー向けメッセージと、調査に必要な内部ログを分ける。
- **MUST** パスワード、トークン、Cookie、Authorizationヘッダーをログへ出さない。
- **SHOULD** ログには事象、対象、結果を含め、調査可能な情報を残す。
- **SHOULD** 想定内の入力エラーと、想定外のシステムエラーを区別する。

## 8. テスト

自動テスト環境は現在未導入です。導入後は、次を必須ルールとして扱います。

- **MUST** 不具合修正には、可能な限り再発防止テストを追加する。
- **MUST** 認証、認可、金額計算など重要な業務ロジックを優先してテストする。
- **SHOULD** 実装内部ではなく、公開された振る舞いと入出力をテストする。
- **SHOULD** 単体テストは外部APIやDBへ直接依存させない。
- **SHOULD** 成功ケースだけでなく、境界値と失敗ケースも確認する。

## 9. セキュリティ

- **MUST** `.env` など秘密情報を含むファイルをコミットしない。
- **MUST** 認証だけでなく、対象データへアクセスできるか認可も確認する。
- **MUST** ユーザー入力をHTML、URL、SQLなどへ使用するときは用途に応じて安全に扱う。
- **MUST** 依存パッケージの追加は目的、保守状況、ライセンス、既存機能で代替できないか確認する。
- **SHOULD** エラー内容や応答時間から機密情報を推測されない設計にする。

## 10. 完了条件

変更は次の条件を満たしたときに完了とします。

- 要件と受け入れ条件を満たしている。
- 型チェック、Lint、ビルド、導入済みテストが成功する。
- デバッグ用コード、不要なログ、未使用コードが残っていない。
- エラー状態と境界値を確認している。
- UI変更はPCとスマートフォン相当の表示で確認している。
- 仕様や利用方法が変わった場合はREADMEや関連文書を更新している。
- Pull Requestに確認方法と影響範囲が記載されている。

## 11. ルールの更新

ルールは固定ではありません。レビューで繰り返し指摘される事項や、障害の原因になった事項を
追加候補とします。追加するときは、目的、適用範囲、自動チェックの可否を明確にします。
不要になったルールは削除し、この文書を実際の開発方法と一致させます。
